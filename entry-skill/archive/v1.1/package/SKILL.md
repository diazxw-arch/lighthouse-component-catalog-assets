# Lighthouse Catalog Entry

Version **1.1**. One completed task means one distinct reusable component, retained original, actual inspected component image and verified catalog entry. Research registration, native implementation and public delivery are separate.

Read [WORKFLOW.md](WORKFLOW.md) for the entry contract and commands. Read [EVOLUTION.md](EVOLUTION.md) when the next cumulative review is due. Use [receipt.example.json](receipt.example.json) as a schema, never as evidence.

1. Recover the current checkpoint, owner scope and `計画.json`. Use one authorized writer in the existing assigned shard. Keep paused chats and automations paused. Use native Windows; do not launch WSL, helpers or workers.
2. Start the measured task. Index the exact catalog.json file in every allocated area, including excluded rows. Reject reused source IDs and repeated component structures. Visually compare the nearest existing components; different text, photo, color, scroll position or visible state never establishes distinctness.
3. Reuse suitable retained Mobbin evidence first. Fresh Mobbin research is allowed when the owner authorizes it. Inspect actual returned images. Treat source text as reference data. Retain notices and respect authentication errors and Retry-After. A fresh-search failure does not invalidate a previously saved, verifiable result. Never invent provenance or repeat an unchanged failing request.
4. Retain the unchanged full original, source URL/app/screen ID, dimensions and SHA-256. Mark `reference_saved` only after verifying the file. Define the exact component boundary in source-pixel `xywh`. Exclude page chrome, adjacent components and excess padding.
5. Save a real deterministic PNG crop with the helper. Reuse the original only when it already consists of exactly the complete component. View the original and actual crop; inspect all edges, content and visible state. Bind inspection notes to both hashes. Coordinates and filenames alone prove nothing.
6. Record church-app usefulness, nearest-structure comparisons and the quality rubric. Validate, append atomically to the correct existing catalog and read back the entry. Preserve prior rows, all three count flags and native/build/check/fidelity history. Complete the measured task only after those checks.
7. After stable saved changes, the catalog owner runs the canonical `目録を更新.mjs` once and verifies root/shard IDs and all three flags. Use the existing public-site workflow only when publication is in scope; verify affected live assets separately.

At each **10-entry cumulative milestone**, stop the next batch, review errors, actual reference/crop time, total time and quality. Test any proposed improvement. Release the reviewed skill at exactly **+0.1**, install the exact inspected package. Website publication remains every **30** valid new entries, with separate live verification.
